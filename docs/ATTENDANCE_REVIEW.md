# Attendance review

Attendance sessions resolve explicit service IDs first. IDs identify members and visitors even when older `person_type` metadata is missing or wrong. Only present check-ins count; duplicates are shown once. Single and batch check-ins reject unknown services, archived services, missing people, invalid dates and future dates. Batch inputs deduplicate people, respect the visible selection and persist as one transaction. An absent or excused row becomes present under its existing ID when the person checks in. Undo removes duplicate copies of the same present check-in together.

Database indexes enforce one attendance record per person/service/date and one headcount per service/date. A private trigger derives member/visitor classification from the IDs. Attendance writes require exactly one identity, a valid status and a nonfuture date. New headcounts require nonnegative whole-number categories and a matching auditorium total. Optimistic versions prevent stale saves; the editor preserves unsaved changes when remote data arrives and offers to load the latest saved headcount.

Headcount forms hydrate after asynchronous loading and retain edits until saved. Dashboard figures use saved headcounts rather than unsaved drafts. Attendance targets are separate from physical seating capacity. Visitors and ushers are separate tally categories, and staff are instructed to count each person once. First-time status and unique online reach are not inferred from a visitor ID or a stream-view count.

Session history includes check-in-only dates as well as headcount dates and follows the chosen service. Analytics use the selected service, with saved headcounts taking precedence over unique check-ins. Follow-up uses present records, excludes members who joined after the selected date and does not claim an unrecorded session was fully attended. Dates and check-in times use Africa/Accra. CSV exports quote text and neutralize spreadsheet formulas. The session export follows the selected session; the all-records export retains raw history for audit.

Visitor registration and its check-in share one transaction. The previous kiosk had a publicly displayed hardcoded exit PIN; the screen is now explicitly staff-assisted and does not claim to isolate the signed-in staff session. It shows success only after the check-in handler accepts the attendee. Attendance actions require the staff module permission, and database authorization remains authoritative. The shared header uses compact controls on small screens.

`scripts/recover-service-history.sql` is a reviewed maintenance script, not an automatic application action. It restores unambiguous missing service references under their original IDs as inactive, unscheduled archive entries. It does not merge overlapping sessions, invent former schedules or move attendance, rosters, giving or money to a similarly named current service. Conflicting names remain unresolved for explicit review. Archived history can be inspected without enabling new check-ins; reactivation requires a real schedule. A current Friday service is configured separately from any archived Friday history.

Verification covers pure attendance and date logic, database integrity/permissions/recovery, and browser workflows for identity totals, headcount loading/edit/save/conflicts, registration, session navigation/history, safe exports, duplicate undo, archived/future-date restrictions, mobile layout and restricted staff access. Browser tests use synthetic records and mocked Supabase calls; live database probes run inside rolled-back transactions.
